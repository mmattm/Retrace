# Simplicity and token efficiency

This file is the shared source of project instructions for all coding agents. Shared skills live in `.agents/skills/`; tool-specific instruction and skill files only point here. When writing, editing, debugging or reviewing a p5.js sketch, read `.agents/skills/p5js-reference/SKILL.md` and follow its relevant references. Resolve those references relative to that shared skill's directory. Explicit user instructions and this project's rules take precedence over the skill's generic defaults. Maintain shared guidance here and in `.agents/skills/`, rather than duplicating it in tool-specific files.

For sketches on any engine, use a minimal visual style by default: a black background with white forms and strokes unless the prompt or a specified reference selects other colors. Avoid inventing palettes, decorative effects, or stylistic embellishments. Follow the requested visual direction and project-specific defaults; add controls only when requested.

Keep code simple, readable and educational. Avoid unnecessary abstractions and dependencies. Read only the files needed for the request. To edit a sketch, consult the relevant project entry in `timeline/projects.json` and its starting version with its optional `ui.js`. Do not browse other projects or older versions without a reason. Keep responses short and checks proportionate.

Use English for new project interface text, documentation and code comments. This requirement does not apply to the conversation with the user. Preserve existing archived versions and prompts.

Per-sketch LLM support is opt-in for each new version. Do not create or automatically copy an `agent.json`, a sketch-specific system prompt or an LLM parameter schema into a new version unless the user explicitly requests it. Do not add parameters or integration code solely for LLM control without that request. Creating a project or a new sketch version does not imply enabling LLM support.

When agent support is explicitly requested, use the following scope:

- **Add agent, with no further restriction:** read the entire target sketch and its optional `ui.js`, then expose all existing tunable configuration variables, including settings outside `CONFIG` and those without UI controls. Exclude animation state, counters, caches and derived values. Do not invent new creative parameters.
- **Only UI parameters:** expose only the variables adjustable through the sketch's existing UI. Any other explicit parameter selection also limits the agent to that selection.
- **Extend the sketch with more configurable variables:** introduce useful creative parameters where the drawing currently uses fixed values, connect them to the drawing and expose them to the agent. Preserve the sketch's visual idea and keep the changes simple.

Generate the agent description, system instructions, parameter schema and integration code to match that scope, with clear meanings, types and sensible limits. Analyze the source when creating the agent version; live requests send the metadata and current parameter values, without rescanning or sending the source. Do not add UI controls unless separately requested.

Include an `examples` array in each requested `agent.json`: a short list of English prompts that demonstrate that version's supported commands within its limits. The shared overlay shows a random quoted example on opening; tapping Shift cycles examples without changing typed text. Enter sends typed text or, when empty, the current example. Shift+Enter adds a line. Keep API response values in the browser console rather than displaying them in the overlay footer.

Show the shared Agent button and enable its T shortcut only when the active sketch version contains its own `agent.json`. Hide and disable both for versions without that file. An explicitly requested agent version exposes `window.sketchAgent.getState()` and `window.sketchAgent.applyParameters(values)` using the same configuration as its controls, and refreshes those controls after agent changes. Its `agent.json` contains a description, `systemPrompt`, and constrained `parameters`. The shared validator supports bounded numbers, booleans and strings constrained by choices or a pattern (including hexadecimal colors). Add minimal type support if needed for the requested scope rather than silently excluding a configuration variable.

When explicitly asked to draw from prompts instead of changing parameters, use `mode: "drawing"` and a constrained `responseSchema` in `agent.json`. Expose read-only scene context through `getState()` and apply validated drawing commands through `applyDrawing(command)`. The validator also supports bounded arrays and objects with explicitly declared properties. Generate drawing data, never executable code. Ordinary requests to add an Agent still use the parameter scope above.

Fullscreen is the default for this project, overriding the p5 skill's generic 640 × 640 default. The shared preview resizes the p5 canvas to fit the viewport and sidebar. Opening the footer scales the preview without resizing the canvas. Use `width` and `height` for drawing coordinates. Sketch controls belong in a `#sketch-controls` container created by `ui.js`: the shared CSS places them in a responsive sidebar, below the canvas on narrow screens. Sidebars start hidden unless the URL contains `controls=true`; the shared Controls button opens them and updates that URL setting. Do not add controls unless requested.

When a sketch has a requested UI, add a short English helper at the top of `#sketch-controls`, before the pane. Use one or two concise sentences to explain its main interaction or what the controls affect. Create a `<p class="sketch-helper">` and reuse the shared 12 px text, 16 px line height and 8 px bottom gap. Let the shared theme set its color in normal and Poster Mode; do not hard-code text colors or duplicate helper styles in `ui.js`. Do not create an interface solely to show a helper.

The shared preview sets pixel density to 2 whenever a main canvas is created, before the sketch draws; the Paper.js runtime applies the same 2× backing resolution. Keep drawing coordinates and controls in logical canvas units; the backing image has twice the width and height. Do not add redundant `pixelDensity(2)` calls to individual sketches. Export starts from those backing pixels; its separate Scale setting enlarges the captured image further.

Reuse the shared iOS interaction styles: canvas gestures must not select text or zoom the page, while editable fields retain native selection and scrollable panels retain scrolling. Keep input text at least 16 px to avoid iOS focus zoom. Do not add per-sketch global touch blockers; the shared shell and iframe provide Safari gesture guards.

Keep Tweakpane groups transparent, without gray fills, shadows or outer panel borders. Text fields use a transparent background and a thin 1 px border matching the shared theme: white normally and dark in Poster Mode. Reuse these shared styles rather than adding per-sketch themes.

Reuse shared Tweakpane sizing on desktop, tablet and mobile: 44 px control heights, 24 px slider handles and 8 px spacing. Base text is 16 px with 12 px labels above full-width controls, 16 px label line height and a 4 px gap. On touch-capable devices, the shared styles raise control text to 17 px and labels/helpers to 13 px with 18 px line height. Main interface actions use at least 44 × 44 px touch targets. Keep iOS system areas black in standalone mode and place interface actions below the top safe area. Reuse these styles for current and future projects; do not add per-sketch sizing or device detection.

# Educational sketch history

All sketches live in `timeline/versions/<project-id>/<version-id>/`. Each version may specify `engine: "p5"`, `engine: "paper"` or `engine: "three"`; missing engine metadata means p5. Preserve the starting engine unless the user requests a change. Each `sketch.js` starts with `// Engine: p5.js`, `// Engine: Paper.js` or `// Engine: Three.js`, matching the metadata. The save tool adds or normalizes this header automatically; the timeline displays the active engine beside the version counter. The header is documentation; metadata selects the loader. `timeline/projects.json` is the single metadata index: an array of projects, each with its `id`, `title` and `versions` array. Filter by project ID rather than reading every history for a single-sketch task. The last entry in the selected project's `versions` array is its active version, loaded at startup. There is no working copy at the root.

Always identify the relevant project from the request or the prompt copied from the timeline. If a historical prompt contains an obsolete sketch path, resolve its project and version IDs through `timeline/projects.json` and use the current `sketch` path there; do not rewrite archived prompts. If several projects exist and the context does not identify which one to edit, ask before changing a sketch. To create a project, choose a stable ID using lowercase letters, digits and hyphens, then provide `--title` on its first save. Do not create demo projects or versions to fill the menu.

For a new project without a specified engine, ask which engine to use. Explain each option in one sentence and recommend the simplest fit for the brief.

- **p5.js** is suited to direct 2D canvas drawing, gesture input and generative animation with a simple draw loop.
- **Paper.js** is suited to editable vector shapes, Bézier paths, typography along curves and SVG export.
- **Three.js** is suited to GPU rendering, shaders, cameras and drawing in 3D or on 3D surfaces.

Once the engine is known, ask in a separate message whether the user has a concrete visual reference, such as an image, artwork or link. Offer the option to proceed without a reference. Skip either question if the brief already answers it. Wait until both are resolved before writing or saving the sketch. Existing iterations keep the engine of the starting version unless the user requests a change.

Create a new version only when the request changes a project sketch or its own controls and their code has actually changed. Questions, explanations and changes to the timeline, shared interface, shared CSS, `index.html`, documentation or tools do not create a version when the sketch and its controls remain unchanged. Do not create an initial backup when working on these shared elements.

1. Copy the sketch from the last entry in the relevant project's history (or the explicitly requested version) and its optional `ui.js` into a temporary folder; include `agent.json` only when agent support is explicitly requested for the new version, then edit and validate that copy. Never edit an existing version directly.
2. Clean up the prompt before saving: correct spelling, grammar, syntax and punctuation; rephrase spoken or informal wording into clear, polished text. Preserve the meaning, every instruction, value and technical reference, without adding intent or removing useful details. If several messages guided the same change, clean them up and keep them in order. Write this text as UTF-8 to a temporary file. Also write a short English summary of the implemented version, usually one sentence, without copied project/version metadata or instructions for another change.
3. Run `node timeline/save.js --project <id> --sketch-file /path/to/sketch.js --prompt-file /path/to/prompt.txt --summary "Short description of this version"` from the project root (add `--title "Project title"` for a new project). For Paper.js sketches, add `--engine paper`; for Three.js, use `--engine three`. p5 is the CLI default. For explicitly requested agent support, add `--agent` and provide an `agent.json` beside the temporary sketch; the flag is required to archive it. The script adds the sketch and its optional neighboring `ui.js` and opted-in `agent.json` under `timeline/versions/<id>/` and appends the version to that project's history. For a new project, start with a new temporary sketch and save it only after validation.
4. Verify that the new version appears in the relevant project's history, that its concise `summary` appears in the index, and that the full cleaned prompt appears both in the index and in the saved `prompt.txt`. The timeline displays the summary; copying it adds the project ID, version ID and sketch path as context for the next request. A copied reference is context and does not itself request a new version.

Save exactly one version per completed request, after validating the sketch. Previous versions are immutable: do not correct them, delete them or rewrite their dates. Do not create fake versions to fill the timeline. If the user explicitly asks not to save a change, respect that request.

Keep all history logic and sketches inside `timeline/`. The timeline HTML lives in `index.html`; `main.js` only imports styles and the timeline module. A sketch-specific interface lives in its neighboring `ui.js`, including its controls and styles. This module exports `createUI(config)`; `sketch.js` loads it using `await import('./ui.js')` inside `setup()` and passes `CONFIG`. Both files stay together in each version. Requested changes to sketch controls belong to that version; shared interface changes do not create a version.

# Verification

Prefer code review, syntax checks, targeted local tests and verification of saved files. Do not open a browser or preview window, or take screenshots, unless explicitly requested by the user. Visual changes or suspected visual issues do not override this rule. When a preview is explicitly requested, keep screenshots, inspections and tool output minimal to save tokens.

# Project environment

The project uses Vite with plain JavaScript: `npm run dev` is sufficient. Do not generate a `dist/` folder during verification. Keep p5.js sketches in global mode. The timeline loads only the selected engine’s npm browser distribution into an isolated iframe. Libraries are managed through npm with a lockfile. p5.js, Paper.js, Three.js and Tweakpane are installed; do not create a parameter panel without an explicit interface request. The timeline discovers all versions through `import.meta.glob`: preserve this behavior when making changes.

Paper.js versions use ordinary JavaScript with the global `paper` object and `setup()` / `draw(deltaSeconds)` functions, without PaperScript or `paper.install(window)`. The shared `timeline/paper.js` runtime creates the canvas and Paper scope, awaits setup, starts playback and handles resizing; do not start another animation loop or create another main canvas. Use `paper.view.viewSize` for logical dimensions and `window.sketchRuntime.redraw()` for immediate updates. The shared runtime bridge in `timeline/runtime.js` connects the engines to playback, FPS, PNG and video export; Paper also exposes SVG export with the same crop. Verify Paper APIs against the installed version and its matching source/reference, including the pinned CanvasView density handling when upgrading Paper.js. Keep Agent support opt-in, controls in neighboring `ui.js`, and requested interactions compatible with touch.

Three.js is primarily a drawing renderer here. Use `setup()` / `draw(deltaSeconds)` in ordinary JavaScript with the global `THREE` namespace. `timeline/three.js` creates a flat scene, fixed orthographic camera and 2× WebGL canvas, exposes them on `window.sketchRuntime`, then loads the sketch and awaits setup. Scene coordinates are logical pixels with the origin at the top left and Y increasing downward; keep drawing geometry at Z=0. Prefer the provided `THREE.Line2`, `THREE.LineGeometry` and `THREE.LineMaterial` for controllable stroke widths, and unlit `MeshBasicMaterial` for filled shapes. Set `side: THREE.DoubleSide` on screen-space line materials: the shared Y-down scene flips mesh winding, while their shader expands strokes directly in screen space. Do not add perspective, lights or orbit controls unless requested. The shared runtime owns playback and resizing; request `window.sketchRuntime.redraw()` for immediate updates. Three supports the shared PNG/video exports, while SVG is available for Paper. Keep Agent support opt-in and manual drawing interactions touch-compatible.
